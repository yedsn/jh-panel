## Context

JianghuJS 管理器在项目新增或编辑时，会根据“自动清理日志”开关创建或删除单项目计划任务 `[勿删]项目[项目名]日志清理`。该实现将清理开关、计划时间和日志保留规则分散在每个项目中；项目数据本身没有保存清理开关，旧任务是否存在成为唯一状态来源。

JianghuJS 管理器也没有服务配置面板。主备管理插件已集中定义计划任务切换和自检规则：任务通过固定名称由 `scripts/switch.py` 开关，自检通过 `HA_CHECK_DEFS` 查询计划任务状态。此次新增的依赖预热任务必须按主备角色调整，而日志清理是本机运维任务，不随主备角色变化。

## Goals / Non-Goals

**Goals:**

- 为 JianghuJS 管理器提供服务配置页面，集中管理两个唯一的全局计划任务。
- 让 `JianghuJS管理器项目预备` 每次执行时动态读取全部已登记项目，仅对存在 `package-lock.json` 的项目安全、顺序地执行 `npm ci`。
- 让 `JianghuJS管理器日志清理` 每次执行时只清理已开启日志清理的项目，并使用统一的时间和保留规则。
- 将项目日志清理开关持久化到 JianghuJS 项目数据，保持已有项目的启用状态。
- 在本地主备切换与自检中强制备用机启用、主机停用项目预备任务。

**Non-Goals:**

- 不修改项目启动、停止、重启、自启动或项目部署逻辑。
- 不将日志清理任务纳入主备开关或主备自检策略。
- 不并行执行多个项目的 `npm ci` 或日志清理，避免资源竞争。
- 不在任务中自动创建不存在的项目日志目录或不存在的 `package-lock.json`。

## Decisions

1. **使用固定名称的两个全局面板计划任务。**
   依赖预热任务固定为 `JianghuJS管理器项目预备`，日志清理任务固定为 `JianghuJS管理器日志清理`。服务配置页通过现有计划任务接口读取、创建、修改和删除它们。
   替代方案是使用插件 `info.json.tasks`。该机制适合安装后固定的内部维护任务，不能满足操作员在页面中配置频率、时间、保留规则和删除任务的需求。

2. **计划任务只调用 JianghuJS 后端受控入口。**
   两个任务的 `sBody` 只进入 `plugins/jianghujs/index.py` 的专用命令；后端读取项目记录并用安全参数处理目录。不会由前端将项目路径逐条拼接进计划任务 shell 内容。
   替代方案是前端生成包含所有路径的 shell 脚本。项目路径变更或新增后会立即过期，且特殊字符会扩大 shell 注入风险。

3. **日志清理参与状态保存到项目记录，规则保存在唯一任务。**
   项目记录增加 `log_clean_enabled` 布尔字段。全局清理任务保存执行周期、时间和三项保留规则；执行时对开启标记的项目依次调用既有 `scripts/clean.py` 清理 `<项目目录>/logs`。
   替代方案是把规则仍保存到每个项目。这样虽然只剩一个触发任务，但仍需处理不同项目规则，且不符合统一维护诉求。

4. **升级时先迁移状态，再在全局任务创建成功后删除旧任务。**
   后端识别旧格式 `[勿删]项目[<项目名>]日志清理`，仅在能唯一匹配项目时迁移，并继承旧任务的启用或停用状态。只有 `JianghuJS管理器日志清理` 创建成功后，才删除已识别的旧项目清理任务。
   替代方案是升级时立即删除旧任务。若新任务创建失败，已开启清理的项目会出现清理中断。

5. **依赖预热任务只由主备策略控制。**
   备用机切换流程增加开启 `JianghuJS管理器项目预备` 的步骤，主机切换流程增加关闭步骤；自检要求备用机启用、主机停用。任务不存在时沿用现有计划任务规则显示提醒，不阻断切换流程。
   替代方案是两端同时启用，或不进入主备策略。前者可能在两台机器同时进行耗时安装，后者无法保证备用机切换前完成依赖预热。

## Risks / Trade-offs

- [风险] `npm ci` 可能耗时较长且占用网络、CPU、磁盘。 → 顺序执行、逐项目记录结果，并允许在服务配置中控制执行频率。
- [风险] 项目目录缺失、没有 `package-lock.json` 或日志目录不存在。 → 单个项目记录为跳过或失败后继续处理下一项目，任务日志给出项目名和原因。
- [风险] 旧单项目任务名称可能因项目改名而不能匹配。 → 保守迁移：仅删除能可靠识别并迁移的旧任务，未识别任务保留并在结果中提示人工处理。
- [风险] 日志清理全局任务被删除时，项目标记仍会保留。 → 保留标记；任务重新创建后立即恢复对已标记项目的清理，无需逐项目重新配置。
- [风险] 主备切换时依赖预热任务尚未创建。 → 切换动作输出“计划任务不存在”，自检以提醒项暴露，且不阻断既有切换流程。

## Migration Plan

1. 先发布项目字段兼容读取逻辑，缺少 `log_clean_enabled` 的现有项目默认按旧任务是否存在决定迁移结果。
2. 用户在服务配置中创建统一日志清理任务时，后端迁移可唯一匹配旧任务的启用状态；确认新任务创建成功后再删除对应旧任务。无法匹配或同名项目不唯一的旧任务保留，并可在服务配置中再次手动迁移。
3. 用户配置依赖预热任务后，主备切换可自动开关该任务；任务未创建时自检保持提醒。
4. 回滚时保留项目的 `log_clean_enabled` 字段；若恢复旧版本，可基于该字段和统一任务配置手工恢复旧单项目任务，避免删除项目日志或项目数据。
