## Context

`nfs-util` 已有多选状态和四种批量操作，但单项删除仍需逐条确认。现有单项删除只移除 DictDataBase 中的管理记录，不卸载当前挂载，也不修改 `/etc/fstab`。批量删除必须保持这一语义，并通过更明确的确认减少批量误删和遗留系统配置的风险。

## Goals / Non-Goals

**Goals:**

- 在已有选择状态基础上提供批量删除管理记录。
- 删除前展示已选数量和名称，并明确说明不会卸载或取消自动挂载。
- 后端对 ID 去重，删除存在记录并报告不存在记录。
- 删除完成后刷新列表并移除失效选择。

**Non-Goals:**

- 不自动卸载 NFS 挂载。
- 不删除或修改 `/etc/fstab`。
- 不删除本地挂载目录或远端共享数据。
- 不改变单项删除的语义。

## Decisions

1. **批量删除使用单个后端接口。**
   新增 `mount_batch_delete`，接收逗号分隔 ID，复用已有批量 ID 去重和记录查询逻辑。接口一次完成有效记录删除并返回 `deleted`、`missing` 摘要。
   替代方案是前端循环调用单项删除接口。该方式请求数量多，结果难聚合，并可能在刷新过程中丢失选择状态。

2. **使用 `safeMessage` 进行数据安全确认。**
   确认内容展示已选数量和经过 HTML 转义的挂载名称，并以醒目文案说明删除只影响管理列表，现有挂载和自动挂载配置仍会保留。
   替代方案是普通 `layer.confirm`。批量删除不可由界面恢复，且容易留下失去管理入口的运行配置，因此需要沿用面板数据删除的高风险确认模式。

3. **批量删除不校验或改变运行状态。**
   已挂载或已开启自动挂载的记录仍允许删除，与单项删除保持一致。风险通过确认说明暴露给用户，而不是隐式执行卸载或阻止操作。
   替代方案是拒绝删除运行中的记录。该方案会改变现有删除语义，并增加用户无法清理异常记录的情况。

4. **删除完成后清理选择并刷新列表。**
   前端根据后端 `deleted` 结果移除已删除 ID，刷新后由既有逻辑自动剔除不存在的选择。不存在记录计入跳过摘要，不作为整批失败。

## Risks / Trade-offs

- [风险] 用户删除仍在运行或仍配置自动挂载的记录后失去管理入口。 → 确认框明确列出“不卸载、不清理自动挂载”，并展示具体名称。
- [风险] 列表刷新前记录已被其他操作删除。 → 后端报告 `missing` 并继续删除其余有效记录。
- [风险] 批量删除不可由插件界面恢复。 → 使用 `safeMessage` 高风险确认，且不删除实际目录或远端数据。

## Migration Plan

1. 发布后端批量删除入口。
2. 发布批量删除按钮、确认流程和资源版本更新。
3. 回滚时移除按钮和接口即可；已删除管理记录不会自动恢复，但实际挂载和 `/etc/fstab` 未被修改。
